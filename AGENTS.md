# Agro Vision Backend - Reglas de Gobierno

### Section 1: Reglas Inviolables

1. **CERO `any`** — TypeScript en modo estricto (`strict: true`, `noImplicitAny: true`). Prohibido usar `any` o conversiones inseguras como `as unknown as Type`.
2. **PRECISIÓN NUMÉRICA ESTRICTA** — Coordenadas, porcentajes de precisión, métricas agronómicas y valores críticos deben modelarse con tipos precisos (ej. `@db.Decimal` en BD, librerías de precisión en código donde aplique).
3. **LÍMITE DE 300 LÍNEAS** — Ningún archivo de código debe superar las 300 líneas. Si un componente o servicio crece más, debe refactorizarse y modularizarse.
4. **CERO `localStorage` PARA SESIÓN** — En backend, manejo de autenticación robusta: Access Token JWT de vida corta y Refresh Token seguro.
5. **CERO EXCEPCIONES GENÉRICAS (Result Pattern)** — En la capa de aplicación y dominio se utiliza el patrón funcional `Result<T, E>`. Prohibido lanzar errores no controlados.
6. **MIGRACIONES FORMALES** — Prohibido el uso de `prisma db push` en entornos compartidos o productivos. Todo cambio de esquema debe realizarse mediante migraciones versionadas (`prisma migrate dev`).
7. **CERO HARDCODING** — Todas las variables de entorno, configuraciones y catálogos deben provenir de archivos `.env`, configuración inyectada o base de datos.
8. **LÓGICA DE DOMINIO EN BACKEND** — Toda validación de negocio, algoritmos de análisis agrícola y reglas de procesamiento residen en el backend.
9. **CERO CASCADE EN AUDITORÍA Y MAESTROS** — Relaciones hacia entidades principales deben configurarse con `onDelete: Restrict` para proteger la integridad histórica de datos.
10. **SIN ATRIBUCIÓN IA** — No incluir firmas, encabezados ni comentarios del tipo "Generated by AI" o "Co-Authored-By AI".
11. **PATH ALIASES `@/*`** — Usar siempre alias de importación configurados en `tsconfig.json`. Prohibido el anidamiento relativo profundo (ej. `../../../`). Solo se permite `./` para archivos hermanos directos en la misma carpeta.
12. **LENGUAJE UBICUO EN ESPAÑOL** — Módulos, carpetas, rutas de endpoints, controladores, casos de uso, repositorios y entidades DEBEN nombrarse en español técnico canónico (`usuarios`, `cultivos`, `parcelas`, `monitoreo`, `diagnosticos`, `sensores`). Estrictamente prohibido el uso de anglicismos en la estructura del dominio.
13. **MENSAJES DE VALIDACIÓN EN ESPAÑOL** — Todos los DTOs de entrada decorados con `class-validator` DEBEN especificar mensajes explicativos en español (`@IsNotEmpty({ message: 'El nombre del cultivo es requerido' })`).
14. **DOCUMENTACIÓN SWAGGER OBLIGATORIA** — Todo controlador DEBE estar decorado con `@ApiTags()`, `@ApiOperation({ summary })`, `@ApiResponse()` (códigos 200/201 y respuestas de error tipadas) y `@ApiBearerAuth()` si es protegido. Todo DTO debe documentar sus propiedades con `@ApiProperty()`. La interfaz interactiva estará disponible en `/api/docs`.

### Section 2: Commits y Colaboración

* **Formato:** `<tipo>(<modulo>): <descripción imperativa en español>` (máximo 72 caracteres).
* **Tipos permitidos:** `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`.
* **Unidades atómicas:** Cada commit debe agrupar código + tipos + pruebas + esquemas correspondientes.

---

### Section 3: Estándar JSDoc Exclusivo

* Usar exclusivamente bloques estructurados `/** ... */`. Prohibido el uso de comentarios dispersos `//` dentro del código.
* Explicar el **POR QUÉ** y la intención del negocio, no limitarse a parafrasear el nombre de la función.
* Etiquetas estándar: `@description`, `@param`, `@returns`, `@throws`, `@example`.
* Idioma: Dominio y descripciones en español técnico, firmas de tipos en TypeScript estándar.

---

### Section 4: Pipeline de Validación

Antes de dar por completada una tarea o realizar un commit:

```bash
pnpm run build
pnpm run lint
pnpm run test
```

Si alguno de estos comandos falla, la tarea **NO** está terminada.
